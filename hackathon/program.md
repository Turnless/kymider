# Midnight Buildathon — rules that matter

Copied from the AKINDO program page (2026-10-01). The binding text is the
Official Rules PDF linked there.

## Rubric

| Criterion | Weight | What is checked |
|---|---|---|
| Engineering & Implementation | 40% | Compact contract compiles, has private-state management, shows the dual-ledger model; well-organized repo with a clear README; Midnight topics on the repo and ecosystem attribution |
| Quality Assurance & Reliability | 15% | Simulation and test files exist, tests pass, product stable under basic use |
| Product & Vision | 15% | Soundness of the idea, connection to Midnight's capabilities, realistic scope and roadmap |
| User Experience & Design | 15% | Intuitive frontend that behaves as expected and connects to the contract end to end |
| Communication | 10% | Clarity and structure of the video and slide deck |
| Business Development & Viability | 5% | Target audience, market potential, adoption path |

## Technical gate (fail = disqualified for that wave)

- At least one Compact contract that compiles.
- Meaningful Midnight-related functionality; not a fork, copy or superficial change.
- The `midnightntwrk` topic on the GitHub repo (Kymider has it).
- A public GitHub repository, a slide deck, and a demo video or video pitch.
- Apache-2.0 for the Midnight-related code (Kymider has it).

## Submit on AKINDO, each wave

- Public GitHub repo link (**connect it in the repo field**, not just in text).
- README: project, setup, architecture, Midnight integration, how judges test it.
- Slide deck and demo video.
- Progress made during this wave.
- For a resubmission: what changed since the previous wave.
